# Phase 2 security review — the Rust control plane (task 2.12), 2026-11-15

**Scope.** What Phase 2 ported: `cp-targets`, `cp-scanning` (queue, dispatcher, scheduler, ingestion port, the built-in
worker's loop), `cp-agents` (the agent protocol and its administration), `cp-outbox`, `cp-gate`, `cp-issues` and
`cp-inventory` as far as ingestion writes them, `crates/crypto`, `crates/protocol` (server half), `crates/runner`, and
their composition in `cp-app` (`main.rs`, `worker.rs`, `ingestion.rs`). Not `cp-platform` (its settings routes were
being ported at the same time), not the agent binary, not Java except as the reference for what Rust must do.

**Method.** The `security-audit` skill: four read-only `security-reviewer` passes — authentication; authorization and
visibility; injection, SSRF, outbound and paths; crypto, secrets and deployment — each told that **a Rust divergence
that weakens a guard Java has is a finding**. Every finding below was then opened at the cited lines and its guard
followed before it counted; the fixed ones were proved by a test that is red without the fix. Branch
`rust/p2-12-security-review`, cut from `rust/p2-9-finish`.

**Result.** Two high and three medium findings, all Rust-only regressions against Java: all five fixed. Two small parity slips fixed with them. The rest is listed with its reason: three are shared with
Java and go to Java first, the others are low and need a decision or a change outside this review's files.

### H1 — the agent protocol found the agent by name, not by its key — fixed

**Found by two areas independently** (authentication, authorization). The bearer chain resolved an agent's key to its
row (`agents::by_api_key`) and then kept only `agent:<name>` in the principal; every protocol route looked the agent
up again **by that name** (`find_by_name`, `where name = ?`, no order). `t_agent.name` has no unique index, neither
Java's nor Rust's `declare` refuses a duplicate, and MySQL's collation folds case and accents.

*Scenario.* An administrator who suspects agent `builder-1`'s key disables it and declares a new `builder-1`. Both keys
now resolve to whichever row MySQL returns first: if the new one, the compromised key keeps working — it claims the new
agent's scans, renews their leases (`claimed_by` is the row found by name), submits results for them (**unsigned** if
only the old row had no pinned key: an empty result resolves the target's backlog), and overwrites the new agent's
executors; if the old one, the legitimate agent is refused as disabled. The same without any disabling whenever two
agents are named alike under the collation. Java hands the controller the `AgentView` found by the key.

*Fix.* `Credential::Agent` carries the id of the row the key is bound to; `authenticate_agent` reads by id;
`find_by_name` is gone with its two cached statements. *Verified*: `protocol_lifecycle` declares a disabled namesake
under the owner's name — **red on MySQL against a lookup by name** (the disabled key answered 200), green now;
`credentials_on_both_engines` and `across_the_switch` pin the id the chain puts in the principal (the latter against a
key Java created). Mutants: 3 in `p2-12-security.py`.

### H2 — the scanned repository could configure its own scanners — fixed

Java's `ScanRunner.analyse` removes `.checkov.yaml`, `.checkov.yml`, `.gitleaksignore` and `.semgrepignore` from the
clone before any scanner reads it (`ScannerConfigurationFiles`, after each was measured silencing the findings planted
in a fixture). The shared runner went from the clone to the scanners with no such step; none of the names appeared in
the Rust sources.

*Scenario.* Anyone who can push to an audited repository — no Vectispire account needed — commits a `.gitleaksignore`
or `.semgrepignore` listing what it wants unseen, or a `.checkov.yaml` with `skip-check` or an `external-checks-dir`
(checkov then runs the repository's Python and can print any report). The step reports a shorter or clean list, which
resolves the target's existing issues of that type and passes the gate (decision 0007). It held for the built-in
worker and for the Rust agent, which share the runner.

*Fix.* `runner::configuration_files::remove_from`, a port of `removeFrom`: the whole clone, no link followed, a link
removed as a link, a directory bearing a name removed with its content, an unreadable directory failing the scan.
`run` calls it through `prepare_tree`, before the scan root is proven. *Verified*: four unit tests (every name at every
depth, a link to outside the clone, a directory bearing a name, a tree that cannot be walked) and one on
`prepare_tree`; 8 mutants (each name, the depth, the walk's error, the directory case, the call itself).

### M1 — a repository URL could name Vectispire's own endpoints — fixed

Java builds the allow-list as `GitHostAllowlist.parse(...).refusing(guard::reservedReason)`: the Docker daemon, the
database and the cluster's API — by name and by resolved address — are refused before the list is read, **whether a
list is set or not**, when the URL is entered and before each scan. Rust's `GitHostAllowlist` had no such question and
`main.rs` composed the list alone, with the guard holding the reserved endpoints built a few lines above.

*Scenario.* An administrator (not the governor) registers `ssh://mysql:3306/x.git`, `git://docker-socket-proxy:2375/x`
or a name resolving to the database's address. Rust accepts and queues it; the built-in worker, inside the control
plane on the database's and the proxy's network, connects there — reachability and port probing read from the scan's
failure kind, and a git token bound to that host sent after a 401. It is the request Java refuses at every outbound
door.

*Fix.* `GitHostAllowlist::refusing`, asked first by `permits` and `refusal` (which creation, update, import and the
dispatch-time check all use); `repository_url::port` (Java's `RepositoryUrl.port`); `OutboundUrlGuard::reserved_reason`
(Java's `reservedReason`); `cp-app`'s `clone_hosts::allowlist` composes them, so `main.rs` changes by one call.
*Verified*: `clone_hosts_composition` (a reserved endpoint refused unlisted and listed, by name and by address, the
on-every-host port, Java's sentence) and the domain's tests (the order, the ports); 6 mutants.

### M2 — a pinned Ed25519 key of small order verified every signature — fixed

`crypto::verify` used ed25519-dalek's non-strict verification and accepted a key of small order. Under the identity
point, `R` = identity and `s` = 0 verify for every message. BouncyCastle refuses such a point
(`Ed25519PublicKeyParameters` → `checkPointFullVar`) and Java's attestation answers `false`.

*Scenario.* An administrator pins, as an agent's public key, a value handed over by whoever runs the agent host — the
identity point among them. Anyone holding that agent's API key then forges its results and failure reports and, worse,
its **sealing-key announcement**, so deployment keys and HTTPS tokens are sealed to a key the attacker owns: the one
thing decision 0031 relies on to vouch for it.

*Fix.* `verify` refuses a key `is_weak()`, as BouncyCastle does; the pin route still accepts it, as Java's does
(changing what the route answers would diverge from Java's reference set). *Verified*: `crypto/tests/small_order.rs`,
two of the eight points of small order against results, failures and announcements; red without the check.

### M3 — sealing to an X25519 key of small order — fixed

`seal_with` never checked `was_contributory()`: to a recipient of small order the agreement is all zeros and the session
key follows from the envelope's own public bytes, so any reader of the claim's answer (a proxy that logs bodies, a
recording) opens the credential. Medium rather than high because it needs a *signed* announcement of such a key — the pinned seed, or M2. BouncyCastle
throws "X25519 agreement failed" and Java abandons the claim. *Fix*: `seal_with` answers `CryptoError::Recipient`, which
`deliver` already turns into the transient failure Java's `abandon` mirrors; `open` refuses an ephemeral key of small
order (an envelope sealed by someone who knows the agreement is zero). *Verified*: `small_order.rs`, each check red
without it; the Java reference vectors still pass.

### L1 — a database failure while resolving a key answers 401 — not fixed

`cp-access`' `closed()` turns a failed key or session lookup into "no principal", so during an outage a valid agent key
gets 401 "API key absent, invalid, or without the agent scope" — the symptom task 2.9 fixed for the second lookup only.
Java's filter lets a `DataAccessException` through as a 500. *Not fixed*: it is Phase 1's chain (every credential kind,
not only agents), and the fix — a `KeyLookup::Failed` the chain answers with a 500 — belongs with the chain's owner.

### L2 — database failures swallowed on agent routes — not fixed

`hello` ignores `record_heartbeat`'s error (answers 200, the contract version and executors not stored), `heard_from`
ignores `record_seen`'s, and a failed `accept_sealing_key` becomes a 400 "needs an X25519 public key" that blames the
agent. Java throws, so a 500. *Not fixed*: small, but `hello` and `heard_from` change error type; a follow-up for the
agents module.

### L3 — the route-authorization test exempts any `names_no_target()` route — not fixed

`route_authorization.rs` gives every route declared `names_no_target()` the same fixed reason, so the rule's "a reason
of ten characters" can never fire, and the scope check runs only for `Scoped` routes. A future
`Route::get("/api/v1/repositories/{id}/x").requires(Access::Account).accepts_api_key(Read).names_no_target()` would pass
while serving every account's data. Java's `AuthorizationCoverageTest` admits only a scope-settling role without
`@AcceptsApiKey`, or an entry in a reviewed `NOT_TARGET_SCOPED` list. *Exposure today: none* — every such route in the
composed registry is `AgentKey`, `Administrator`, `SecurityLead` or `GovernanceRead`, none accepts an API key, and every
role they admit has global scope. *Not fixed*: the reviewed exemption list is a decision for the review.

### L4 — the gate's service drops the visibility proof — not fixed

`POST /api/v1/gate` checks visibility (404) and then hands `evaluate_and_record` a bare `ScanTarget`; `evaluate` is
public too. Java's `GateService.evaluateAndRecord` takes the `VisibleTarget` proof and keeps the evaluation
package-private, "so no other caller can skip it". *Exposure today: none.* *Not fixed*: a signature change across the
gate's tests, best made with the next gate route.

### L5, L6 — parity slips and `Debug` — fixed

The protocol service read the announced key, the pinned key and the signatures with `str::trim`, and `normalize_host`
too: Rust accepted values wrapped in a no-break space that Java refuses. No guard was weaker — the decoders trim as
Java — so it is parity, now `java::trim` / `java::is_blank`. `DeclaredAgent` and `PinnedKey` derived `Debug` over the
agent's API key and a generated seed; nothing printed them, but semgrep's `Secret` rule cannot see a `String`. They now
print without the secret (a unit test and two mutants hold it).

### J1–J3 — shared with Java, to fix there first

- **J1.** The sealing-key update checks the generation but not that the signing key the announcement was verified
  against is still the pinned one: an announcement in flight while an administrator re-pins can commit after the pin's
  reset. Narrow, and *plausible* (not reproduced). Fix in both: add the verified signing key to the update's condition.
- **J2.** The long poll reads the agent once and claims for up to 30 s with that copy; `lock_for_claim` updates by id
  alone, so a disable made meanwhile does not stop the poll already open from receiving the next scan. Fix in both:
  `and enabled = true` in the claim's lock.
- **J3.** An image registry is validated as syntax only, so an administrator can have the Docker daemon pull from an
  internal or loopback endpoint — a blind GET. *Plausible*, not checked on a running daemon.

These are reported to Java's owners rather than fixed here: a Rust fix alone would make Rust's answer differ from
Java's in a module the port holds to Java, and the protocol's are better made once in both.

## Divergences that are not security findings

- **Vault is reached with the built-in trust** (`cp-app/src/main.rs:240`), where the SIEM sender takes the runtime's
  (`VECTISPIRE_TLS_CA_BUNDLE`): a Vault behind a private authority fails closed, with a misleading "cannot be decrypted"
  on the scans. Not fixed here — `main.rs` was being edited by the platform port.
- **An agent's protocol body is capped at 50 MiB** (`cp-agents/src/web/protocol.rs:419`) where the chain allows a result
  256 MiB (decision 0038): a large SBOM between the two is a 400 where Java accepts it.
- **`dispatcher.rs`' `sbom_text`** rebuilds a `serde_json::Value` without the recursion limit; the read path is tested at
  depth 999 against Java, this one is not exercised on a 2 MiB runtime thread. No overflow was shown.
- **The import's visibility mode is not composed** (`cp-app/src/main.rs:372`, `TargetsConfig { visibility: None }`): it
  fails closed, and nothing calls it until the import routes are ported, which must wire it.
- **`cp-agents`' `administration_reference` fails on PostgreSQL** (`tests/administration_reference.rs:266`, `char = uuid`):
  a test bug of the previous task, on an engine the checks no longer run.

## Checked and found sound

- **Credential confinement**: an agent key is refused on every route not marked `AgentKey`; an integration key needs
  `accepts_api_key` and its scope; the SCIM and scrape tokens are principals on their own paths only. Every Phase 2
  route's marker and scope match its Java annotation, `POST /gate` included (`WriteAccount` + `SCAN`, 404).
- **Visibility** on the 29 target routes, the scan routes and the gate: lists apply the allowance in the query and cut
  the page after it; every update, scan trigger and deletion goes through `require_visible_*` (one 404 for absent and
  hidden); a key restricted to one target cannot scan another; separation of duties holds (`WriteAccount` excludes the
  governor and the auditor).
- **The agent never comes from the body**: heartbeat, result and failure use the principal's agent; leases are held by
  `status = scanning and claimed_by = <agent>`; ingestion takes the target from the scan's row.
- **Signatures and sealing**: checked over the raw body before parsing, per context with the scan id; the sealing
  announcement needs a pinned key (412), binds agent, generation and key, refuses an older generation; credentials are
  sealed for the verified key or withheld, never sent in clear; HTTPS tokens bound to host and user.
- **Encryption at rest and the signing key**: AES-256-GCM with a fresh nonce and the context as associated data, no
  fallback without it; keys redacted in `Debug`, compared in constant time, refused at start when weak or when Vault is
  asked for without its settings; no secret in a view, an audit line, an outbox payload or a problem body.
- **Outbound and repository content**: URL validation on create, update, import and dispatch, and again at clone time
  against link-local and metadata addresses; no redirect followed; a token sent only to its bound host after a 401;
  strict SSH host keys; sub-paths proven inside the clone; no SQL built from strings; request bodies bounded and agent
  results read through Java's limits; failure reasons scrubbed; CSV cells neutralised.
