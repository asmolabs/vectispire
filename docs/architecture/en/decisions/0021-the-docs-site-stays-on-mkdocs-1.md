# 0021 — The documentation site stays on MkDocs 1, until something else can publish it in two languages

**Date:** 2026-09-24 · **Status:** accepted · **Decider:** Laurent Boucher

## Context

The user guide in `docs-site/` is built by MkDocs 1.6 with Material for MkDocs and
`mkdocs-static-i18n`, and published to GitHub Pages by `docs.yml`. It is **bilingual by
structure**: every page exists as `page.md` and `page.fr.md`, the English tree is served at the
root and the French one under `/fr/`, the interface strings are translated per language, and a
switcher moves between the two. That structure is what the plugin provides; nothing in MkDocs
itself does.

MkDocs 2.0 removes the plugin system. Material for MkDocs is in maintenance, and its team's
successor is **Zensical**, which reads `mkdocs.yml` and maps the plugins it knows to modules of
its own. `mkdocs-static-i18n` has declared itself frozen for the same reason.

So the question was not whether to leave MkDocs 1 eventually, but whether Zensical could take the
site now. It was **tried rather than read about**: Zensical 0.0.64, on an unmodified copy of
`mkdocs.yml`, `docs-site/` and `docs-site-overrides/`.

- It built the site, fast, with no configuration change.
- **It ignored the i18n plugin.** The French pages came out beside the English ones —
  `/guide/repositories.fr/` next to `/guide/repositories/` — instead of forming a `/fr/` tree; no
  language switcher, no French interface strings.
- French cross-page links were resolved against the English pages, which is why it reported three
  missing anchors: `#comment-la-note-du-scorecard-est-calculee` looked up in a page that has
  `#how-the-scorecard-grade-is-computed`.

Its plugin compatibility page lists `search` and sixteen others as supported and does not list
`i18n` at all; its roadmap names suffix-based languages and interface localisation under
"publishing at scale", with no date and an explicit statement that it promises none.

## Decision

**Stay on MkDocs 1.6, Material 9 and `mkdocs-static-i18n` 1.x, pinned, and re-evaluate when a
successor publishes a suffix-structured bilingual site.**

The pin is enforced in two places, because one was not enough: `requirements.in` bounds
`mkdocs<2`, but `requirements.txt` is generated by `uv` without the header Dependabot reads, so
`.github/dependabot.yml` also refuses a MkDocs major explicitly.

**Re-evaluate when** Zensical — or another generator — lists `mkdocs-static-i18n`, or its own
suffix-based languages, as supported. The test is the one run here: build the unmodified site and
check that `/fr/` exists, that the switcher works and that the three French anchors resolve.

## What was rejected

**Migrating to Zensical now.** It would have published a site whose French half is a set of
orphan pages under English URLs, with the interface in English — worse than the site today, for
the benefit of leaving a version that still works.

**Migrating to another generator** (Docusaurus, Starlight). Both handle i18n, but the site would be
rewritten — navigation, admonitions, the Material overrides, the `mkdocs.yml` comments that carry
its reasoning — to escape a problem that has not yet arrived: MkDocs 1.6 still builds, is pinned
by hash, and changes nothing by standing still.

**Dropping French from the site.** The product documents regulatory obligations to French-speaking
auditors; `AGENTS.md` makes both languages a requirement, not a courtesy.

## Consequences

- MkDocs 1.6 receives no further releases. A vulnerability in it, or in a pinned dependency,
  would have to be judged against what the build does — it reads this repository's markdown and
  nothing else — rather than fixed by an upgrade.
- The `docs` workflow now builds on `develop` and on pull requests as well, so a dependency bump
  that breaks the build is seen before `main`, not at publication.
