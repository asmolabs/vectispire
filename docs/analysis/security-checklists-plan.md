# Security checklists — implementation plan

The lots that build [decision 0032](../architecture/en/decisions/0032-security-checklists.md), in
the order they can ship. Each lot is releasable on its own: it leaves the product coherent, it
carries its tests, its documentation in both languages and, when a route changes, the regenerated
OpenAPI contract and client types. The plan is written against the proposal; the owner's answers to
its open questions may move a line, and the lot that depends on the answer says which.

Sizes are rough: **S** is one or two days, **M** three to five, **L** one to two weeks, each
including its tests, its mutation checks and its documentation.

## Order at a glance

```
  L1 examined types ──┐
                      ├──► L6 measurements ──► L7 measurements on screen
  L2 CI report imports┘          ▲
                                 │
  L3 model + reader ──► L4 templates ──► L5 project checklists ──► L8 document ──► L9 later
                           (back+front)        (back+front)
```

L1 and L2 have no dependency on the checklist and can start at once, in parallel with L3.

## L1 — A scan records what it examined (backend, S)

- `t_scan.examined_types` (migration, common), written by `ScanDispatcher` from the set
  `ScanIngestor` already computes; `ScanView` and the scan detail carry it.
- `ScanCatalog.newestExamining(repositoryIds, type, since)`: the newest completed scan per repository
  in which a built-in type produced, batched by 1,000 ids.
- Tests: an absent step leaves the type out (mutation: write every type), a scan from before the
  migration reads as unknown, the query past 1,000 repositories on the engines.
- Ships as: the scan page shows which steps looked. `integrationTestAll`.

## L2 — Coverage and test reports from declared internal sources (backend + frontend, L)

- `t_sarif_source.kinds`, `t_coverage_import`, `t_test_report_import`, `t_test_suite_result`
  (migration, common unless an engine diverges); `ApiKeyScope.REPORT_IMPORT`, never by default.
- Readers in `common/domain`: JaCoCo, Cobertura, lcov, JUnit XML and a zip of JUnit files — DOCTYPE
  tolerated and never loaded, entities refused, counts bounded, empty reports refused.
- Routes `coverage-imports` and `test-report-imports` in `plugins`, the refusals of 0017 §7 in the
  same order; body limits in `RequestBodyLimitFilter`; `COVERAGE_IMPORTED`, `TEST_REPORT_IMPORTED`,
  `REPORT_IMPORT_REFUSED`; SIEM `VECTI-SEC-027`.
- `plugins` API: the latest coverage and test report per repository, as views (open question 7 may
  move this to a module of its own).
- Frontend: the source form gains the kinds; the repository page lists the latest imports.
- Docs: CI integration page (upload commands, `scripts/vectispire-cli.sh` subcommands), the SARIF
  sources administration page renamed in content to "declared sources", fr/en.
- Tests: the HTTP suite for every refusal (session, undeclared, wrong kind, missing scope, hidden
  repository, out of scope, oversized, empty, XXE, zip bomb), the real `ObjectMapper` on the views.

## L3 — The model and the workbook reader (backend, M)

- `common/domain/checklists`: `ChecklistAnswer`, the item, the version, the layout, the pairing of
  two versions (unchanged, changed, added, removed, paired by hand), the content digest.
- The OOXML reader: zip guards, no DTD, the layout proposal from the file's structure (validation
  ranges, merged cells, runs of filled rows), fill-down of grouped columns.
- Test fixtures are **generated by the tests** from invented controls, never a real template
  checked in; one fixture carries a validation extension, a formula date and a cell comment.
- Ships as: nothing visible — a library with its tests. Could merge into L4 if preferred.

## L4 — Templates and versions (backend + frontend, L)

- Module `core.checklists` with its `package-info`, lines in `ArchitectureTest.MODULES` and
  `ModularityTest.MODULES`; `${bytes}` in `MigrationDialect`; `t_checklist_template`,
  `t_checklist_template_version`, `t_checklist_item`.
- Routes: import (raw body, 10 MB), preview, confirm layout and answer words, pair items, derive,
  publish (four-eyes per open question 9), retire, list, read; `CHECKLIST_TEMPLATE_*` audit;
  SIEM `VECTI-SEC-024`.
- Frontend: an administration screen — upload, the proposed layout on a grid, the answer words, the
  pairing with the previous version, publish.
- Docs: administration page "Checklist templates", fr/en.
- `integrationTestAll` (binary column on three engines, `SchemaParityIntegrationTest`).

## L5 — Project checklists, answered by people (backend + frontend, L)

- `t_checklist`, `t_checklist_answer`, `t_checklist_evidence`, `t_checklist_file`; the
  `open_slot` constraint.
- `RowVisibility.requireWhollyVisibleProject` and `VisibleProject`; `AuthorizationCoverageTest`
  and `routesLeaveTheRefusalToTheirServices` cover the new routes.
- Open, answer, history, evidence (links and files, served as downloads only), submit, return,
  sign-off with four-eyes (open question 2), reopen, move to a version with carried answers; the
  `ProjectDeleted` listener (open question 10). Audit `CHECKLIST_*`; SIEM `VECTI-SEC-025`, `026`.
- Frontend: a checklist tab on the project — lines grouped by domain and objective, answer and
  comment, history per line, evidence, the submit and sign-off actions, the carried lines awaiting
  confirmation.
- Docs: guide page "Security checklists", fr/en; the four-eyes page gains the sign-off.
- Tests: four-eyes forced (same person refused, second person accepted, mutation removing the
  comparison), a partial reader answered 404, append-only history, carrying across two versions.
- Ships as: a fully manual checklist, which is already the feature most organisations lack.

## L6 — Measurements (backend, L)

- `ChecklistRule` and its kinds; binding on a draft version (L4's screen gains it in L7).
- The owners' grouped queries: `IssueCatalog` counts by tool scope and severity with settled triage
  out, the plugin outcomes per repository, the SARIF, coverage and test imports, the components of the
  newest SBOM. Batched ids.
- `t_checklist_measurement`; computed on demand, at submission, inside the sign-off; the
  reconciliation of answer and measurement; the refusals of open questions 3 and 4.
- Tests, each with its mutation: a project without repositories is `NO_DATA`, an absent step is
  `NO_DATA`, a plugin `not_applicable` everywhere is `NO_DATA`, a stale scan is `NO_DATA`, a settled
  finding leaves the counts, a status unknown to this version stays open, a sign-off whose
  measurement changed after submission is refused.
- `integrationTestAll` (the grouped queries on the engines).

## L7 — Measurements on screen (frontend, M)

- The rule binding form in the template screen (kinds, scopes, thresholds, maximum age, the KPI text
  beside it), presets (secrets at zero).
- On the project checklist: the measurement beside each bound line, its evidence, the one-click
  answer, the divergence badges.

## L8 — The signed document (backend + frontend, M)

- The renderer in `common/domain`: the template package patched cell by cell, inline strings, the
  formula date replaced by the sign-off instant, the calculation chain dropped when needed, the added
  `Evidence` sheet, deterministic entries; `checklist.json`.
- Signing with `SigningKeyService`, `ProductVersion` in the statement; `t_checklist_document`
  written inside the sign-off; the document route (`@AcceptsApiKey(EXPORT)`); `CHECKLIST_EXPORTED`.
- Tests: every part not rewritten is byte-identical to the template's, the validation extension
  survives, the date is a value, a draft is unsigned and says so, the signature verifies against the
  published key.
- Frontend: download, and the verification command.
- Docs: the guide page gains the document and its verification.

## L9 — Later, each its own decision or lot

- Report plugins (the P3 block): containers receiving `checklist.json`, their output signed by core
  — a decision record of its own before any code.
- Signed checklists in the compliance evidence bundle.
- Version ordering for component versions; coverage per file; assignment from the contact column.

## What every lot runs before it is pushed

`./gradlew build`; `integrationTestAll` whenever a migration, a `persistence` package or
`core/config` moved (L1, L2, L4, L5, L6, L8); the contract regenerated with
`-Dvectispire.openapi.write=true` and `npm run generate:api` when a route changed; the frontend
job's whole list — lint, `format:check`, build, test — when `vectispire-angular/` changed;
`check-doc-links.py` and `check-doc-facts.py`.
